# Detailed Technical Breakdown: .NET Modular Monolith with DDD

## 1. Core Architectural Principles and Design Patterns

### **Primary Architectural Patterns**

#### **CQRS (Command Query Responsibility Segregation)**
- **Commands** (Write Model): Processed through DDD tactical patterns with full domain model
  - Uses repositories and aggregates
  - Enforces business rules
  - Generates domain events
- **Queries** (Read Model): Direct SQL queries against database views using Dapper
  - Optimized for read performance
  - No domain model involvement
  - Returns DTOs directly

#### **Domain-Driven Design (DDD) - Tactical Patterns**
- **Aggregates**: [MeetingGroup](cci:2://file:///d:/Mostafa/Git/PlayBackground/modular-monolith-with-ddd/src/Modules/Meetings/Domain/MeetingGroups/MeetingGroup.cs:10:4-127:5), `Meeting`, `Member`, `MeetingGroupProposal`
- **Entities**: Rich domain objects with behavior and identity
- **Value Objects**: `MeetingGroupLocation`, `MeetingTerm`, `MoneyValue`
- **Domain Events**: `MeetingGroupCreatedDomainEvent`, `MeetingAttendeeAddedDomainEvent`
- **Business Rules**: Encapsulated as objects (e.g., `MeetingCanBeOrganizedOnlyByPayedGroupRule`)
- **Repositories**: Abstraction for aggregate persistence

#### **MediatR Pattern**
- All commands and queries are handled through MediatR
- Provides loose coupling between API and handlers
- Enables decorator pattern for cross-cutting concerns

```csharp
public interface ICommand<out TResult> : IRequest<TResult>
{
    Guid Id { get; }
}

public interface ICommandHandler<in TCommand, TResult> : IRequestHandler<TCommand, TResult>
    where TCommand : ICommand<TResult>
{
}
```

#### **Decorator Pattern**
Applied to all command handlers in this order:
1. **LoggingCommandHandlerDecorator** - Logs execution context
2. **ValidationCommandHandlerDecorator** - FluentValidation rules
3. **UnitOfWorkCommandHandlerDecorator** - Transaction management + domain event dispatching

```csharp
builder.RegisterGenericDecorator(
    typeof(UnitOfWorkCommandHandlerDecorator<>),
    typeof(ICommandHandler<>));

builder.RegisterGenericDecorator(
    typeof(ValidationCommandHandlerDecorator<>),
    typeof(ICommandHandler<>));

builder.RegisterGenericDecorator(
    typeof(LoggingCommandHandlerDecorator<>),
    typeof(IRequestHandler<>));
```

#### **Clean Architecture**
Each module follows Clean Architecture with dependency inversion:
- **Domain Layer** (innermost) - No dependencies
- **Application Layer** - Depends only on Domain
- **Infrastructure Layer** - Depends on Application and Domain, implements interfaces

## 2. Modular Structure Implementation

### **What Defines a "Module"?**

A module is a **self-contained bounded context** with:

1. **Own Database Schema** - Complete data isolation (e.g., `meetings`, `administration`, `payments`, `userAccess`)
2. **Own Composition Root** - Separate IoC container (Autofac) per module
3. **Clean Architecture Structure**:
   - [Domain](cci:7://file:///d:/Mostafa/Git/PlayBackground/modular-monolith-with-ddd/src/Modules/Meetings/Domain:0:0-0:0) - Domain model
   - `Application` - Use cases, commands, queries
   - `Infrastructure` - Data access, external integrations
   - [IntegrationEvents](cci:7://file:///d:/Mostafa/Git/PlayBackground/modular-monolith-with-ddd/src/Modules/Meetings/IntegrationEvents:0:0-0:0) - Public contracts for inter-module communication

4. **Single Public Interface**:
```csharp
public interface IMeetingsModule
{
    Task<TResult> ExecuteCommandAsync<TResult>(ICommand<TResult> command);
    Task ExecuteCommandAsync(ICommand command);
    Task<TResult> ExecuteQueryAsync<TResult>(IQuery<TResult> query);
}
```

5. **Initialization Method**:
```csharp
MeetingsStartup.Initialize(
    connectionString,
    executionContextAccessor,
    logger,
    emailsConfiguration,
    eventsBus);
```

### **Module Isolation Guarantees**

**Architecture Tests** enforce module boundaries using NetArchTest:


## 3. Event-Driven Communication Between Modules

### **Three Types of Events**

#### **A. Domain Events (In-Process, Within Module)**
- Published by aggregates when state changes
- Handled synchronously within the same transaction
- Implements MediatR `INotification`

```csharp
public class MeetingGroup : Entity, IAggregateRoot
{
    private MeetingGroup(...)
    {
        this.AddDomainEvent(new MeetingGroupCreatedDomainEvent(this.Id, creatorId));
    }
}
```

**Dispatching**: During [UnitOfWork.CommitAsync()](cci:1://file:///d:/Mostafa/Git/PlayBackground/modular-monolith-with-ddd/src/BuildingBlocks/Infrastructure/UnitOfWork.cs:18:8-25:9):
```csharp
public async Task<int> CommitAsync(CancellationToken cancellationToken = default)
{
    await this._domainEventsDispatcher.DispatchEventsAsync(); // Dispatch domain events
    return await _context.SaveChangesAsync(cancellationToken); // Then save
}
```

#### **B. Integration Events (Cross-Module, Asynchronous)**
- Published to **In-Memory Event Bus**
- Consumed by other modules asynchronously
- Implements **Outbox/Inbox pattern** for reliability

**Publishing Flow**:
1. Domain event occurs → Domain event handler creates `DomainEventNotification`
2. [DomainEventsDispatcher](cci:2://file:///d:/Mostafa/Git/PlayBackground/modular-monolith-with-ddd/src/BuildingBlocks/Infrastructure/DomainEventsDispatching/DomainEventsDispatcher.cs:11:4-82:5) saves notification to **Outbox table**
3. Background job (`ProcessOutboxJob`) reads Outbox
4. Publishes `IntegrationEvent` to Event Bus
5. Other modules' Inbox receives and processes

```csharp
public class MeetingGroupProposedIntegrationEvent : IntegrationEvent
{
    public Guid MeetingGroupProposalId { get; }
    public string Name { get; }
    public DateTime ProposalDate { get; }
    // ...
}
```

**Subscription**:
```csharp
private static void SubscribeToIntegrationEvents(ILogger logger)
{
    var eventBus = MeetingsCompositionRoot.BeginLifetimeScope().Resolve<IEventsBus>();
    
    SubscribeToIntegrationEvent<MeetingGroupProposalAcceptedIntegrationEvent>(eventBus, logger);
    SubscribeToIntegrationEvent<SubscriptionExpirationDateChangedIntegrationEvent>(eventBus, logger);
    SubscribeToIntegrationEvent<NewUserRegisteredIntegrationEvent>(eventBus, logger);
}
```

#### **C. Internal Commands (Deferred Processing)**
- Commands scheduled for later execution within the same module
- Stored in `InternalCommands` table
- Processed by background job (Quartz.NET)

### **Outbox Pattern Implementation**

**Saving to Outbox** (during domain event dispatch):
```csharp
foreach (var domainEventNotification in domainEventNotifications)
{
    var type = _domainNotificationsMapper.GetName(domainEventNotification.GetType());
    var data = JsonConvert.SerializeObject(domainEventNotification);
    
    var outboxMessage = new OutboxMessage(
        domainEventNotification.Id,
        domainEventNotification.DomainEvent.OccurredOn,
        type,
        data);
    
    _outbox.Add(outboxMessage);
}
```

**Processing Outbox** (background job):
```csharp
const string sql = """
    SELECT [Id], [Type], [Data] 
    FROM [meetings].[OutboxMessages] 
    WHERE [ProcessedDate] IS NULL 
    ORDER BY [OccurredOn]
    """;

var messages = await connection.QueryAsync<OutboxMessageDto>(sql);

foreach (var message in messages)
{
    var @event = JsonConvert.DeserializeObject(message.Data, type) as IDomainEventNotification;
    await this._mediator.Publish(@event, cancellationToken);
    
    // Mark as processed
    await connection.ExecuteAsync(sqlUpdateProcessedDate, new { Date = DateTime.UtcNow, message.Id });
}
```

**Guarantees**:
- **At-Least-Once Delivery** (Outbox)
- **At-Least-Once Processing** (Inbox)
- **Eventual Consistency** between modules

## 4. Dependency Management Strategy

### **Dependency Injection Container**
- **Autofac** - Each module has its own container
- **Composition Root** per module

### **Shared Infrastructure (BuildingBlocks)**

**BuildingBlocks.Domain**:
- `Entity` - Base class with domain events
- `IAggregateRoot` - Marker interface
- `IDomainEvent` - Domain event contract
- `IBusinessRule` - Business rule interface
- `ValueObject` - Base class for value objects

**BuildingBlocks.Application**:
- `IExecutionContextAccessor` - User context (UserId, CorrelationId)
- `IDomainEventNotification<T>` - Notification wrapper
- `IOutbox` - Outbox abstraction

**BuildingBlocks.Infrastructure**:
- [DomainEventsDispatcher](cci:2://file:///d:/Mostafa/Git/PlayBackground/modular-monolith-with-ddd/src/BuildingBlocks/Infrastructure/DomainEventsDispatching/DomainEventsDispatcher.cs:11:4-82:5) - Dispatches domain events
- [UnitOfWork](cci:2://file:///d:/Mostafa/Git/PlayBackground/modular-monolith-with-ddd/src/BuildingBlocks/Infrastructure/UnitOfWork.cs:5:4-26:5) - Transaction management
- [IEventsBus](cci:2://file:///d:/Mostafa/Git/PlayBackground/modular-monolith-with-ddd/src/BuildingBlocks/Infrastructure/EventBus/IEventsBus.cs:2:4-11:5) - Event bus abstraction
- [InMemoryEventBusClient](cci:2://file:///d:/Mostafa/Git/PlayBackground/modular-monolith-with-ddd/src/BuildingBlocks/Infrastructure/EventBus/InMemoryEventBusClient.cs:4:4-33:5) - In-process event bus implementation

### **Module Dependencies**

Each module references:
- ✅ `BuildingBlocks.*` assemblies
- ✅ Other modules' [IntegrationEvents](cci:7://file:///d:/Mostafa/Git/PlayBackground/modular-monolith-with-ddd/src/Modules/Meetings/IntegrationEvents:0:0-0:0) assemblies (for event contracts only)
- ❌ **NO direct references** to other modules' Domain/Application/Infrastructure

### **Registration Example**


Each module's Autofac module registers:
- Command/Query handlers
- Repositories
- Domain services
- Decorators
- Infrastructure services

### **Key Flow Steps**

1. **Controller** receives HTTP request, extracts data, creates Command
2. **Module Interface** ([IMeetingsModule](cci:2://file:///d:/Mostafa/Git/PlayBackground/modular-monolith-with-ddd/src/Modules/Meetings/Application/Contracts/IMeetingsModule.cs:2:4-9:5)) receives command
3. **CommandsExecutor** creates new DI scope and resolves MediatR
4. **Decorator Pipeline** executes (Logging → Validation → UnitOfWork)
5. **Command Handler** loads aggregate from repository
6. **Domain Model** executes business logic, enforces rules, raises domain events
7. **UnitOfWork** dispatches domain events, saves to Outbox, commits transaction
8. **Response** returns to controller

## 7. Modular Monolith vs Microservices

### **Advantages of This Approach**

| Aspect | Modular Monolith | Microservices |
|--------|------------------|---------------|
| **Deployment** | Single deployment unit, simpler CI/CD | Multiple services, complex orchestration |
| **Transactions** | ACID within module, eventual consistency between | Distributed transactions, sagas |
| **Performance** | In-process calls, fast | Network calls, latency |
| **Development** | Easier debugging, single codebase | Harder to debug across services |
| **Data Consistency** | Easier to maintain | Complex (eventual consistency) |
| **Infrastructure** | Simpler (one database, one app) | Complex (service mesh, API gateway, etc.) |
| **Refactoring** | Easier to move code between modules | Harder to change service boundaries |
| **Team Autonomy** | Moderate (shared codebase) | High (separate repos) |
| **Scalability** | Scale entire app | Scale individual services |

### **Trade-offs**

**Modular Monolith Advantages**:
- ✅ **Simpler operations** - One deployment, one database
- ✅ **Better performance** - No network overhead between modules
- ✅ **Easier development** - Single IDE, easier debugging
- ✅ **ACID transactions** within module
- ✅ **Lower infrastructure costs**
- ✅ **Easier to refactor** - Can extract to microservice later if needed

**Modular Monolith Disadvantages**:
- ❌ **Cannot scale modules independently**
- ❌ **Single point of failure** (though can run multiple instances)
- ❌ **Technology lock-in** (all modules use same stack)
- ❌ **Larger deployment unit** (though still manageable)

**When to Choose Modular Monolith**:
- Team size: Small to medium (< 50 developers)
- Domain complexity: Moderate to high
- Performance requirements: High (low latency needed)
- Operational maturity: Limited DevOps resources
- Uncertain boundaries: Domain boundaries not yet clear

**When to Migrate to Microservices**:
- Need independent scaling of specific modules
- Different technology requirements per module
- Large teams requiring full autonomy
- Clear, stable domain boundaries
- Mature DevOps practices in place

## Summary

This is a **production-ready, enterprise-grade modular monolith** that demonstrates:

- ✅ **Strong module boundaries** with architecture tests
- ✅ **Clean separation** of concerns (CQRS, Clean Architecture)
- ✅ **Rich domain models** following DDD tactical patterns
- ✅ **Reliable inter-module communication** (Outbox/Inbox pattern)
- ✅ **Comprehensive cross-cutting concerns** (logging, validation, transactions)
- ✅ **Testable design** (unit, integration, architecture tests)
- ✅ **Scalability path** (can extract modules to microservices)

The architecture balances **pragmatism** (simpler than microservices) with **sophistication** (proper boundaries, event-driven), making it ideal for teams that need modularity without microservices complexity.
